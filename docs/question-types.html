    0. 한 줄 요약

    챗에 들어오는 질문을 ⓐ 새 데이터 조달이 필요한가 × ⓑ 조달 절차를 사람이 미리 저작해 뒀는가 두 축으로 QT1~QT4로 분류하고, 유형마다 다른 설계 전략을 적용한다: QT1 = 라우팅 + 결정론 실행, QT2 = 복합 절차의 spec 선언(workflow화), QT3 = 무계획 컨텍스트 추론 + 지식 주입, QT4 = 폴백(현재 ReAct, plan-first 후보). 계획의 저작자는 기본이 사람(spec)이고, LLM은 QT4에서만 예비 저작자다. 모든 유형의 품질 판정은 QT 라벨이 달린 라우팅 골든셋 (#32)이 맡는다.

    전략 선언

    spec 존(QT1/2)을 akg·asf로 넓히고, 잔여(QT4)는 통제된 agent로 받아내되, obs로 발굴하고 골든셋으로 판정하며 승격을 돌려 agent 존을 계속 좁힌다 — 지식(QT3)은 akg 코퍼스가 별도로 채운다.

    자율성은 목표가 아니라 예산이다. 약한 고정 온프렘 모델 환경에서는 예측 가능한 부분을 workflow로 내리고, 예측 불가능한 잔여만 agent로 남기고, 그 경계를 측정으로 계속 spec 쪽으로 옮기는 것이 최적이다. 행위자별 역할:

    행위자역할담당 존
    asf (agent-skill-foundry)생산 — 절차를 spec으로 저작(공장, 템플릿+검증기)QT1/2 확장
    akg (agent-knowledge-governance)유통 — spec 허브(rev·active·런타임 fetch) / 별도로 지식 코퍼스 공급QT1/2 배달 · QT3 품질
    obs (#48)발굴 — QT4 반복 조합 계측 = 승격 백로그 공급QT4 축소의 입력
    골든셋 (#32)판정 — 승격·라우팅 변경마다 회귀를 숫자로 확인전 존의 게이트
    BE (이 레포)소비·실행 — 라우팅, 결정론 실행기, agent 폴백, 계측전 존

    1. 좌표 — 이 문서가 다루는 설계 축

    에이전틱 시스템 설계는 두 축으로 나뉜다. 이 문서는 그중 두 번째 축의 전략 지도다.

    • 컨텍스트 엔지니어링 — 각 스텝에서 모델이 무엇을 보는가. 시스템 프롬프트 조립(ChatPrompt), 툴 규칙 소유, 주입 섹션, 히스토리 관리가 여기다.
    • 제어 흐름 설계 — 다음 스텝을 누가·언제·어떻게 정하는가. 루프 구조, 계획의 저작자, 결정론/LLM 분담. QT 분류는 이 축의 도구다.

    이 시스템의 정체는 문헌의 ReAct도, Plan-and-Execute도 아니다. 두 패턴은 모두 "계획을 LLM이 런타임에 짓는다"를 전제하는데(한 스텝씩이냐 한 번에냐만 다름), 이 시스템은 계획을 사람이 설계 시점에 spec으로 컴파일해 두고 (steps[].binds), LLM에는 좁은 역할만 남긴다. Anthropic의 workflow-vs-agent 구분으로는 routing + deterministic workflow execution이고, 계보상 고전 task-oriented dialogue 구조와 같다:

    고전 dialogue 시스템이 시스템에서맡는 곳
    의도 분류 (intent classification)어느 스킬인가 = 라우팅LLM (+ 예정: L0/L1 필터)
    슬롯 채우기 (slot filling)spec inputs에 질문·폼·스냅샷 값 대입LLM
    대화 정책 (dialogue policy)다음에 뭘 요청할까 = 조달 진행 판정결정론으로 이관 중 (#38 panel-judge)
    응답 생성 (NLG)결과 서술LLM

    북극성은 LLM 판단 부담↓ · 결정론 제약↑다. 약한 온프렘 모델 전제에서 라우팅+슬롯 채우기는 자유 계획 저작보다 훨씬 좁은 과제라 감당 가능하고, 사람이 계획을 미리 컴파일해 두는 것은 약점 보완이 아니라 환경에 맞는 최적 설계다.

    2. 분류 축과 QT 정의

    질문(정확히는 턴)을 두 축으로 분류한다:

    1. ⓐ 새 데이터 조달이 필요한가 — 이미 대화에 있는 것(이전 답변·스냅샷·조회 결과)만으로 답할 수 있으면 "불필요".
    2. ⓑ 조달 절차를 사람이 미리 저작해 뒀는가 — 단일 spec이 커버하는가, 복수 스킬이지만 정형 절차인가, 아무도 안 써둔 조합인가.

    분류는 대화 단위가 아니라 턴 단위다. 한 대화에서 첫 턴이 QT1이고 후속 턴이 QT3일 수 있으며, 한 턴 안에서 QT3 서술과 QT1 조달이 섞일 수도 있다 (§7 경계 규칙).

    3. 유형별 전략 총괄표

    질문 유형설계 패턴 (방법론)LLM의 역할 결정론(코드·spec)의 역할담당 트랙골든셋 지표 (#32)
    QT1 단일 스킬 조달 Routing + workflow 실행
    (intent classification + slot filling)    		 스킬 선택 · 인자 채우기 · 결과 서술 steps[].binds 체인 실행, 로드 시 배선 검증 #33 L0 필터 · #34 L1 라우터 · akg #43 스키마 v3 top-1 라우팅 정확도, 슬롯 정확도
    QT2 정형 복합 절차 Workflow화 — 스킬 간 오케스트레이션을 spec 선언으로 (Programmatic Tool Calling 원리) 진입 선택 · 결과 서술 (LLM 추론 2회로 압축) 복합 spec이 스킬 N개를 순서 실행 #36 · #21 inspect · akg equipment-check 완주율, 스텝 수 (LLM 체이닝 대비)
    QT3 해석 (조달 불필요) 무계획 — 컨텍스트 추론 + 지식 주입 전부 — 자유 서술이 곧 처리 지식 공급(akg 팩트·코드표·이상 카탈로그), 히스토리·스냅샷 관리 akg 코퍼스 · #21 카탈로그 · #41 캐시/캡 과발화율 — 툴을 안 부르는 게 정답인 케이스
    QT4 spec 밖 즉석 조합 폴백 — 현재 ReAct, 후보 Plan-and-Execute/ReWOO (LLM이 binds 형식 미니 spec 즉석 저작 → 검증 → 결정론 실행) 계획 저작 · 결과 서술 계획 검증기 · 계획 실행기(기존 인프라 재사용) · 폴백 진입 판정 #39 · #35 스텝 예산 plan on/off 비교 — 완주율 · 왕복 수 · LENGTH율

    표를 관통하는 원리: 위로 갈수록 계획의 저작자가 사람이고, QT4만 LLM이 예비 저작자다. 운영 목표는 QT4 발생을 spec 저작으로 승격해 QT2→QT1로 끌어올리는 플라이휠이다(§7).

    4. QT1 — 단일 스킬 조달

    정의: 새 데이터가 필요하고, 단일 스킬 spec이 그 조달 절차를 통째로 커버하는 질문. 예: "CVD-01 지난주 센서값 추이 보여줘" → fdc-trace-reading 라우팅.

    처리 경로: LLM이 스킬을 고르고(spec.inputs 계약으로 인자를 채우면) SkillLoader.runSkill이 steps[].binds 체인을 결정론으로 실행한다. 배선은 로드 시점에 검증된다(인자 실재 · 앞 스텝만 참조 · SQL :var 정확 일치 — 어긋나면 기동 실패).

    현재 상태: 가동 중이되 구간별 지위가 다르다 — 결정론 실행부(코드)는 검증 체계가 있고 구멍이 목록으로 열거된 상태, LLM 구간(발동·슬롯·서술)은 뭐가 얼마나 안 되는지 말할 측정 수단 자체가 없는 상태다. 정복의 다음 수는 후자의 측정 체계(미니 골든셋)다.

    정복 범위 — 단일 스킬 우선 (2026-08-02 결정)

    QT1 정복은 스킬 하나를 잘 돌리는 것부터다. 멀티 스킬 간 선택(라우팅·스케일링)은 그 다음 단계의 논의로 분리한다 — 아래 파이프라인은 호출이 이미 확정된 뒤 (스킬 결정·절차 결정)의 턴 내부를 다룬다.

    제공 조달된 데이터를 어떤 형태로 모델에 주입하나 — 증강 LLM의 Retrieval 팔. ACI로 정의한다(아래) 코드 표면은 존재하나 계약 미명문화 · 경로 간 비대칭

    조달의 결정론부는 "정복"이 아니라 "구멍이 열거 가능한 상태"가 정확하다. 열거된 백로그: ① 컬럼 층위 배선 검증 미구현 (#7 ②) — 로드 검증을 통과하고도 실행 시점에 터질 수 있는 구멍, ② steps[] 의미론 이중성(직접 실행 = 첫 행 무조건 바인드, pick 개념 없음)과 branches 죽은 필드, ③ 실 Oracle 미실증(fixture만 검증), ④ 조달 경로(#38/#44) 운영 실증 전.

    ACI 정의 — 제공 단계의 열린 설계 과제

    ACI(Agent-Computer Interface, SWE-agent → Anthropic 부록 용어) = 모델이 보고 만지는 모든 표면. 현재 코드에서 표면은 이미 중앙화되어 있어, 정의 작업은 재구조가 아니라 계약 명문화 + 미결정 지점 결정이다:

    표면실물현재 계약
    시스템 프롬프트ChatPrompt.system 정체성 + 툴이 스스로 내놓은 guidance() 집계 — 툴 없으면 규율도 안 실림
    맥락 섹션ChatPrompt.contextSection 마지막 사용자 메시지 앞의 별도 system 메시지 — SCOPE·DATA·PROGRESS·INPUTS 4블록, SECTION_* 머리표 상수가 테스트 표식
    툴 결과 되먹임SkillLoader.buildResult [조회 결과] + [출력 지침] + produces + [하지 말 것] + [예시] — 서술 계약이 툴 결과 안에 실려 감
    툴 노출(이름·설명·스키마)spec→컴파일 라우팅 편 소관 — 이 문서의 다음 단계 논의

    결정해야 할 쟁점 4건:

    • push vs pull 비대칭 — 직접 실행 결과는 행 전량을 JSON으로 툴 결과에 붓고(push, SkillLoader.stringify), 첨부/조달 스냅샷은 스키마만 펴고 query_snapshot으로 당겨오게 한다(pull, Design B). chat/data 가동 후엔 같은 데이터가 출처에 따라 다른 형태로 도달한다 — 통일할지, 비대칭을 의도로 못 박을지.
    • push 경로의 행 상한·직렬화 포맷 — 현재 무상한. 사내 실DB 이관 전 결정 필요.
    • 서술 계약의 전달 위치 — produces·avoid·예시가 툴 결과에 실리는 현 구조 유지 vs 시스템 프롬프트로 이동(멀티턴 이력 오염 고려).
    • SECTION_* 상수의 지위 승격 — ACI 계약의 정식 앵커로 선언.

    스케일링 전략 — 다음 단계 (멀티 스킬 라우팅)

    스킬이 늘수록 선택 정확도가 무너지는 문제의 대비책(등록 순서대로). 단일 스킬 정복 뒤의 논의다:

    • L0 결정론 스코프 필터 (#33) — 질의 대상·입력으로 후보를 사전 축소. LLM 개입 없음. 트리거: 스킬 6+.
    • L1 후보 선별 라우터 (#34) — 어휘(BM25)→임베딩, 적응형 K. 트리거: 스킬 10+. 선결: 사내 GW /embeddings 유무.
    • 스키마 쪽 절반 = akg #43 — description 골격 v3(notFor·예시·네임스페이스). 라우팅 신호는 spec이 실어야 하므로 스킬 양산 전에 결정한다.

    측정: 단일 스킬 구간은 미니 골든셋(#32의 선행판)부터 — 양성 케이스 (output.examples[].ask 재사용), 음성 케이스(QT3 질문에 툴을 안 부르는 게 정답), 결핍 케이스(입력 부족 시 request_input이 정답), 서술은 produces 포함 여부로 기계 채점. 러너는 #32와 공용으로 설계해 멀티 스킬 확장 시 top-1 정확도·혼동행렬로 그대로 넓힌다.

    5. QT2 — 정형 복합 절차

    정의: 한 스킬로는 안 끝나지만 순서가 정해져 있고 반복되는 질문. 예: "CVD-01 점검해줘" — 분포 확인 → 센서 상태 → 이벤트 대조 → 종합, 항상 이 순서. QT1과의 차이는 스킬 여러 개를 엮는다는 것, QT4와의 차이는 엮는 방법이 알려져 있고 반복된다는 것. 반복되므로 사람이 미리 저작해 둘 가치가 있다.

    목표 경로: 절차 자체를 복합 spec으로 선언 (#36). LLM 추론은 진입 선택 1회 + 결과 서술 1회로 압축되고, 조회 N종의 순서 실행은 코드가 맡는다. Anthropic Programmatic Tool Calling과 같은 원리로, 스킬 내부에서 이미 하는 일 (binds 체이닝)의 적용 범위를 스킬 사이로 넓히는 것이다.

    현재 상태: 복합 spec이 없어 QT2 질문은 실질적으로 QT4 경로로 처리되고 있다 — LLM이 스텝마다 다음 스킬을 추론(예: 점검 시나리오 = LLM 추론 4회, 그중 선택 판단 3회). #36의 본질은 QT2를 QT4 처리에서 QT1 처리로 옮기는 것이다.

    열린 논점: spec 포맷에 "다른 스킬 참조" 개념이 필요한가(akg 스키마 소관) vs BE가 내부적으로 합성 툴을 만드는 걸로 충분한가. akg equipment-check 문서 타입이 점검 항목 카탈로그로서 절차 선언의 데이터 소스가 될 수 있다.

    트리거: #21 inspect 구현 시점. 단발 조회가 대부분인 지금은 엮을 것이 없다.

    6. QT3 — 해석 (조달 불필요)

    정의: 새 데이터를 가져올 필요가 없는 질문. 이미 대화에 있는 것(이전 답변· 붙여넣은 스냅샷·조회 결과) 위의 추론. 예: "이건 뭐예요?", "이 값 왜 튀었어요?", "그래서 문제가 뭔데요?". 최대로 가야 query_snapshot 단발 재조회다.

    처리 경로: 계획도 라우팅도 불필요 — LLM이 히스토리와 스냅샷 스키마 카탈로그 위에서 자유 서술한다. 이 경로는 spec 체계가 막은 적이 없다: 결정론으로 내린 것은 조달 경로뿐이고, 해석·서술은 처음부터 LLM 자유 영역이다. 따라서 멀티턴 후속 질문에서 시스템이 대답 불능이 되지 않는다 — 후속 질문 대부분이 QT3이기 때문이다.

    승부처는 제어 흐름이 아니라 지식이다. "이 값이 문제인가"를 판정하려면 정상 범위·코드표·알려진 이상 패턴이 필요한데, 이는 루프 설계가 아니라 지식 공급(akg 팩트 코퍼스, equipment-check 문서 타입, #21 이상 카탈로그)이 만든다. 알려진 갭: valueRules 없이 코드표 부재 상태로 서술 중 — akg 코퍼스가 후속이다.

    운영 리스크 두 가지:

    • 라우터 과발화 — 해석만 하면 되는 턴에 스킬을 또 돌리는 것. 골든셋에 "툴을 안 부르는 게 정답"인 멀티턴 케이스를 넣어 감시한다. 시스템 프롬프트에서 "툴 없이 컨텍스트에서 답해도 된다"가 항상 열려 있어야 한다.
    • 컨텍스트 성장 — 히스토리 전량 주입 + 스냅샷 전량 재전송은 턴이 쌓일수록 커진다. 멀티턴이 길어질수록 #41 (content-hash 캐시 + context≤50)의 우선순위가 올라간다.

    7. QT4 — spec 밖 즉석 조합 (폴백)

    정의: 새 조달이 필요한데 그 조합을 아무도 spec으로 안 써둔 질문. 예: "CVD-01이랑 CVD-02 지난주 데이터 비교해서 어느 쪽이 레시피 변경 영향 컸는지" — 개별 스킬은 있지만 "설비 2대 × 기간 정렬 × 이벤트 대조 × 비교 서술"로 엮은 절차는 없다. 사람이 모든 조합을 예상해 저작할 수 없으므로 이 구멍은 반드시 남는다.

    "폴백"의 의미: QT1~3이 커버하지 못한 질문만 받는 2순위 경로라는 뜻이다. spec이 커버하는 질문(QT1·2)에는 plan 단계가 아예 돌지 않는다 — 결정론이 이미 아는 것을 약한 모델에게 다시 묻는 낭비이기 때문이다. QT4에서만 계획의 저작자가 사람(설계 시점)에서 LLM(런타임)으로 바뀐다.

    현재 상태: 순수 ReAct — LLM이 MAX_STEPS=4 안에서 한 스텝씩 추론. 전체 조망이 없어 스텝 낭비·중도 이탈이 생기는 구간이다.

    업그레이드 후보 = plan-first (#39, 논의 단계): 실행 전에 전략 수립 → 투두 목록 → 항목별 실행. 문헌의 Plan-and-Execute/ReWOO 계열로, "스텝 간 의존이 있는 다단계 + 작은 실행 모델"이라는 교과서적 적용 대상과 이 환경이 일치한다. 단, 원형은 강한 계획자를 전제하므로 약한 계획자 갭을 다음으로 메운다:

    • 계획을 자유 프로즈로 받지 않는다 — binds 형식의 미니 spec을 즉석 저작시키고, 기존 배선 검증기 계열로 검증한 뒤, 기존 결정론 실행기로 돌린다. 약한 모델 대비 템플릿+검증기 철학과 실행 인프라 재사용이 동시에 성립한다.
    • 발동 조건도 결정론으로 — 예: 라우터가 확신 있는 단일 매치를 못 찾았고 해당 복합 spec도 없을 때만 plan 단계 진입.
    • 스텝 예산과 연동 (#35) — MAX_STEPS=4에서 계획 1콜은 예산의 25%다. 계획을 별도 호출 대신 첫 실행 스텝에 얹는 절충(첫 응답에서 계획 목록 + 첫 툴 콜 동시 산출)도 후보다.

    채택 판정: 골든셋에서 plan on/off 비교(완주율·왕복 수·스텝 분포·LENGTH율). 숫자 없이 채택하지 않는다.

    실패 폴백 = 2단 정책: ① 시도(agent 또는 plan-first) → ② 계획 검증 실패·스텝 소진 시 정직한 한계 고지로 내려앉는다 — "이 조합은 지원 절차가 없습니다" + 가장 가까운 스킬 제안 + 필요 데이터 요청 카드(기존 QT3 서술·조달 부품 재사용). 약한 모델이 허우적대다 내는 그럴듯한 오답이 agent 존의 최악 사례이므로, 이를 구조적으로 차단한다.

    8. 운영 루프 — 경계 규칙과 승격 플라이휠

    QT3 ↔ QT1/2 경계 = "새 데이터가 필요해지는 순간"

    "이 값 왜 튀었어요?"는 QT3이지만, 답하다가 그 시점 이벤트 로그가 필요해지면 그 턴은 QT1(이벤트 스킬 라우팅)로 넘어간다. QT는 턴 단위 분류이고, 한 턴 안에서 QT3 서술과 QT1 조달이 섞일 수 있다.

    QT2 ↔ QT4 경계 = "반복되는가"

    처음 보는 조합은 QT4다. 같은 조합이 로그에 반복해서 찍히면 spec 승격 후보가 된다. 이것이 운영 플라이휠이고, §0 전략 선언의 실행 형태다:

    라우팅 세금: 승격은 공짜가 아니다. 스킬이 늘수록 라우팅(QT1의 심장) 정확도가 떨어지는 것이 스킬 스케일링 문제의 출발점이므로, QT1/2 확장에는 라우팅 보강이 반드시 동반된다. 납부 시점은 골든셋의 top-1 정확도가 알려준다(스킬 6+에서 L0, 10+에서 L1).

    9. 측정 — 골든셋 QT 라벨링

    골든셋(#32)의 각 케이스에 QT 라벨을 달면 "타입별 정답률"이 나오고, 그것이 곧 "어느 존이 약한가"의 측정이 된다:

    라벨그 존의 정답률이 말해주는 것
    QT1라우팅·슬롯 품질 — L0/L1 도입 시점 판단 근거
    QT2#36(workflow화) 필요성의 정량 근거 — LLM 체이닝의 실패율
    QT3과발화율 — 해석 턴에 툴을 부르는 비율
    QT4#39(plan-first) 채택 여부의 판정 숫자

    케이스 소스: 첫 턴 질문은 spec output.examples[].ask 재사용(스킬 추가 = 테스트 공짜). 멀티턴 케이스는 별도로 저작해야 한다 — 특히 "툴을 안 부르는 게 정답"인 QT3 후속 질문 케이스가 없으면 과발화를 측정할 수 없다.
