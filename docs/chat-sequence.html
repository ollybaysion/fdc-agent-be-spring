레지스트리는 두 종류의 지식을 한 곳에서 관리한다. 절차 지식 — "이런 질문이 오면 이 순서로 조회하라"는 스킬. 이게 곧 에이전트의 툴이 된다. 도메인 지식 — 코드값·컬럼이 무슨 뜻인지(코드표·용어집). 답변의 근거는 전부 여기서 나온다.

절차 지식(스킬) → 툴 카탈로그
  • 스킬 하나 = 툴 하나. 레지스트리에서 받은 스킬을 그대로 컴파일한다 — 코드를 고칠 필요가 없어서, 스킬이 늘면 에이전트가 할 줄 아는 일도 늘어난다
  • 이 질문에 쓰이는 스킬은 explain-sensor — 툴 이름 fdc_explain_sensor, 인자 snsr_id 하나
  • 툴 정의에 실리는 건 이름·설명·인자뿐이다 — 조회 절차(SQL)는 스킬 본문에 남고, 모델에게 가지 않는다
원문 — 이 질문에 쓰인 툴 정의 
{ "type": "function",
  "function": {
    "name": "fdc_explain_sensor",
    "description": "센서 하나를 자연어로 설명한다 — FDC_SENSOR에서 시작해 정의된 순서·분기대로",
    "parameters": {
      "type": "object",
      "properties": {
        "snsr_id": { "type": "string", "description": "센서 ID (예: S-0001)" } },
      "required": [ "snsr_id" ] } } }

description은 모델이 툴을 고르는 유일한 근거다. 설명이 어중간하게 끊긴 건 스킬 설명의 첫 줄만 싣기 때문 — 그래서 첫 줄이 그 자체로 완결돼야 한다. SQL은 이 정의 어디에도 없다.

“이 센서에 대해 설명해줘”

폼 입력 — 설비 ETCH-01 · 챔버 CH-A · 센서 S-0007

1POST /api/fdc/v1/chat · 질문 + 폼

질문 문장만으로는 어느 센서인지 알 수 없다 — "이 센서" = S-0007이라는 건 사용자가 폼에서 고른 값이 알려준다. 챔버는 센서 목록을 좁히는 데만 쓰이고 프롬프트에는 실리지 않는다.

원문 — FE가 보낸 요청 본문 
POST /api/fdc/v1/chat
Content-Type: application/json

{

    { "role": "user", "content": "이 센서에 대해 설명해줘" }
  ],
  "context": [
    { "equipment": "ETCH-01",
      "chambers": [ { "name": "CH-A",
                      "sensors": [ { "name": "S-0007" } ] } ] }
  ],
  "timeRange": { "start": "", "end": "" }
}

폼 값은 프롬프트의 [분석 대상 — 사용자 폼 입력] 블록이 되어 마지막 user 메시지 앞의 별도 system 섹션으로 들어간다(질문 텍스트와 분리 — 데이터 스냅샷 스키마 카탈로그도 같은 섹션). 센서 칸은 PARAM_INDEX로 찍히는데 explain 툴의 인자 이름은 snsr_id다 — 같은 값을 두 이름으로 부르는 지점이라 이어주는 건 모델의 몫이다.

툴 호출 1회 [이 질문은 한 번으로 끝난다 · 모델이 툴을 더 부르면 이 구간이 되풀이 — 최대 4번]

원문 — 1회차 요청 본문

  "tool_choice": "auto",
  "temperature": 0,

폼 블록이 별도 system이 아니라 user 메시지 꼬리에 붙어 있는 것에 주목 — 약한 모델도 "요청의 일부"로 확실히 읽게 하려는 배치다.

3tool_calls · fdc_explain_sensor(snsr_id="S-0007")

모델은 답을 쓰지 않고 툴을 지목한다 — 이름 하나와 인자 한 벌.

원문 — LLM의 툴 호출 응답 
{
  "choices": [
    { "message": {
        "role": "assistant",
        "content": null,
        "tool_calls": [

            "type": "function",

              "name": "fdc_explain_sensor",

모델이 한 일은 툴 하나를 고르고 폼의 값을 그 툴의 인자 이름으로 옮긴 것뿐이다. arguments는 객체가 아니라 JSON 문자열이라 에이전트가 한 번 더 파싱한다. id는 뒤에 결과를 짝맞출 키다.

4스킬 본문 요청 · explain-sensor
5스킬 본문 · 조회 절차 3단계 + 해석 규칙 + 출력 형식

모델이 본 건 툴의 이름·설명·인자뿐이었다. 어떻게 조회하는지는 이 본문에 적혀 있고, 모델은 이 본문을 보지 않는다 — 사람이 정해둔 절차가 그대로 실행된다.

1

EVT_TYPE_CD S=셋업 · I=정보 변경 · M=정비 · 그 외=기타

스킬은 그 값이 어디서 오는지 모른다 — 같은 요청이 이 경계 뒤에서 사내 DB 직접 조회든, 사람이 한 번 받아둔 파일이든, 데모용 샘플이든 똑같이 처리되고, 돌아오는 건 언제나 같은 모양의 행이다.

원문 — 1단계 조회와 결과

rows   [ { "SNSR_ID": "S-0007", "EQP_ID": "ETCH-01",

  FROM fdc_equipment WHERE eqp_id = :eqp

세 단계가 본문에 적힌 순서 그대로 돌았다. 단계 사이의 값 전달은 코드가 하고, 모델은 이 연쇄에 관여하지 않는다.

원문 — 3단계 조회와 결과 
SELECT TO_CHAR(evt_time,'YYYY-MM-DD') AS d, evt_type_cd, evt_label
  FROM fdc_setup_event WHERE eqp_id = :eqp

코드값 "S"가 무슨 뜻인지는 여기 없다 — 그건 다음 화살표가 가져온다.

12도메인 지식 조회 · 이번 결과에 쓰인 컬럼·코드만
13의미 · EVT_TYPE_CD 코드표 · USE_YN · 단위

데이터는 값을, 지식 레지스트리는 그 값의 뜻을 준다. EVT_TYPE_CD = "S"가 무엇인지는 DB 어디에도 없다 — 코드표는 레지스트리에서 온다.

원문 — 지식 레지스트리가 돌려주는 지식의 형태 
{
  "table": "FDC_SETUP_EVENT",
  "columns": {
    "EVT_TYPE_CD": {
      "description": {
        "text": "설비 셋업·변경 이벤트의 유형 코드",
        "tier": "confirmed",
        "evidence": "fdc-app/src/event/EventType.java:22",
        "by": "hong", "at": "2026-07-14"

    }
  }
}

값마다 확신 단계가 붙는다 — 빈칸 → 추정 → 확정(사람이 확인해 올린 것). 답변에는 확정된 것만 쓴다. 지금은 이 의미가 스킬 파일 안에 임시로 적혀 있고, 레지스트리가 붙으면 스킬은 지식을 참조만 하게 된다.

결과 조립 — 사실 + 의미를 한 덩어리로
  • [조회 결과] 스텝별 행 + [값 해석 규칙] 코드표 + [출력 형식] 템플릿을 프로즈로 이어붙인다
  • 같은 행을 표(tables)로도 따로 모아둔다 — 이건 LLM에 보내지 않고 done에 실어 화면으로 직행한다

원문 — 최종 답변 응답 
{
  "choices": [
    { "message": {
        "role": "assistant",
        "content": "센서 **S-0007**은 식각기 1호(ETCH-01, LAM EtcherX-2000)의 PRESSURE 센서(단위 mTorr)로, 현재 **사용 중**입니다. 최근 설비 이벤트는 2026-05-01 셋업(레시피 셋업)입니다. ⚠ 센서 종류·단위 코드의 표준 의미는 확인되지 않아 값 그대로 표기했습니다."

답변의 사실은 데이터에서, 뜻은 지식에서 왔다 — 코드 S가 "셋업"으로 풀린 건 값 해석 규칙을 따른 것이고, 규칙에 없는 PRESSURE·mTorr는 "의미 미확인"으로 남았다(지식 레지스트리가 채울 자리). 모델이 한 건 형식 맞춰 문장으로 옮긴 일뿐이다.
