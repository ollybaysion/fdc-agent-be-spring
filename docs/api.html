    0. 한 줄 요약

    이 서버의 HTTP 표면은 네 개가 전부다 — 헬스체크, 스킬 카탈로그, 라인 목록, 그리고 채팅(SSE). 채팅 하나가 계약의 본체이고, 그 안의 데이터 조달 왕복 (dataRequests ↔ dataSnapshots, inputRequests ↔ inputs)이 이 문서에서 가장 공들여 읽어야 할 부분이다. 서버는 무상태다 — 진행 상태를 저장하지 않고, 매 요청에 실려 온 스냅샷에서 "어디까지 왔나"를 유도한다.

    FE 관점의 계약 문서는 demo-fe 레포의 API.md에 따로 있다. 그쪽은 FE mock 라우트까지 포함한 넓은 표면을 다루고, 이 문서는 이 서버가 실제로 구현한 것만 다룬다.

    사람이 고를 수 있는 스킬 목록. 채팅이 툴로 컴파일해 쓰는 것과 같은 spec을 편다(출처는 SkillSource — akg 허브가 붙어 있으면 허브, 아니면 classpath 번들). FE의 "설비 추가" 진입이 이 응답으로 입력 카드·데이터 요청 카드를 세운다 — api/SkillsController.java:14-19.

    200 OK
{
  "skills": [
    {
      "skill": "fdc_explain_sensor",      // 툴 이름(언더스코어) — inputs[skill][key] 회신 키
      "name": "fdc-explain-sensor",       // spec 이름(케밥)
      "unit": "설비",
      "focus": "센서 상태 해설",
      "description": "…",                 // 합성 라우팅 문장 — 화면에선 부연으로만
      "argumentHint": "…",                // 선택
      "anchorTable": "…",                 // 선택
      "inputs": [ { "key": "snsr_id", "required": true, "description": "…" } ],
      "steps": [
        {
          "title": "…",
          "produces": "…",                // 선택
          "sql": "SELECT … WHERE id = :snsr_id",  // :var 가 남은 미완성 SQL
          "argBinds": { "snsr_id": "snsr_id" },   // bind 이름 → 스킬 인자 이름
          "priorStepBinds": []                    // 앞 스텝 결과에서 오는 bind
        }
      ]
    }
  ]
}
    필드의미
    skill툴 이름(언더스코어). InputRequest.skill과 같은 값 — 여기서 만든 입력 카드의 회신 inputs[skill][key]가 곧장 들어맞는다
    inputs[]스킬 인자 = FE 입력 카드 하나(아직 값이 없다면). required가 있는 것부터 채운다
    steps[].sqlbind 자리가 :var로 남은 미완성 SQL. argBinds로 사용자가 채운 값을 메운다
    steps[].priorStepBinds이 bind는 앞 스텝 결과에서 온다 — FE가 채울 수 없으니 그 카드는 "앞 조회가 먼저"라고 알린다

    6. POST /api/fdc/v1/chat

    계약의 본체. 에이전트 실행(툴 조회 포함)은 스트리밍 시작 전에 끝난다 — 실패하면 아직 헤더를 안 보냈으므로 정상 HTTP 상태로 에러를 낼 수 있고, 성공하면 최종 텍스트를 code point 단위 token 이벤트로 흘린 뒤 구조화 데이터를 done에 번들한다 — api/ChatController.java:26-32.

    6.1 요청 본문

    필드타입의미
    messages (필수) {role, content}[] 대화 히스토리, 최근이 끝. role = user | assistant | system | tool(소문자)
    dataSnapshots ChatDataSnapshot[] 사용자가 붙여넣어 등록한 조회 결과 중 동봉으로 켠 것 — §6.2
    inputs {skill: {key: value}} 입력 카드 회신 스칼라 값. 스킬(언더스코어 툴 이름)로 네임스페이스 — 같은 key를 쓰는 스킬끼리 충돌하지 않는다
    scope {equipments?, analyses?} 이 질문이 무엇을 놓고 하는 질문인지 — 질의 대상 트레이. 설비 통째(equipments[])와 분석 카드(analyses[]: {id, equipment, skill, focus, inputs})가 섞여 산다. 없으면 대화 맥락 전체를 본다

    입력 한도 — 위반 시 400 (api/ChatController.java:39-41):

    항목한도에러 코드
    messages 길이≤ 100messages_too_many
    메시지당 content≤ 10,000자message_content_too_long
    messages 자체비면 안 됨messages_required

    6.2 dataSnapshots — 스냅샷의 세 상태

    스냅샷 한 건 = {queryKey, label, capturedAt, columns, rowCount, rows}. cell 은 원문 NULL을 뜻하는 null을 담을 수 있다((string|null)[][]). 계약의 핵심은 세 상태의 구분이다 — contract/ChatDataSnapshot.java:10-25:

    상태판정의미 · 서버의 행동
    내용 동봉 rows가 있고 비지 않음 임시 DB로 적재돼 query_snapshot 도구로 닿는다. 절차는 다음 단계로 진행
    0행 확인 rows: [] (또는 rows 없이 rowCount: 0) 조회했더니 없었다는 사실. "그 데이터는 없다"는 답의 근거가 되고, 그 조회 절차는 거기서 정상 종료된다
    카탈로그만 rows도 rowCount 판정도 없음 "이런 표가 있다"만 알린 것 — 아직 안 왔으므로 다시 요청할 수 있다

    재요청 억제의 기준은 도착했는가(내용이 있든 0행이든)이다. 0행과 미첨부를 뭉개면, 없음을 확인한 사용자에게 같은 요청이 또 나가거나 모델이 오지 않을 데이터를 기다리게 된다.

    6.3 응답 — SSE 이벤트 3종

    200 OK
Content-Type: text/event-stream; charset=utf-8

event: token
data: {"content":"분"}          ← code point 단위, 답변 길이에 맞춰 간격 자동 조절

event: done                      ← 마지막 1회, 구조화 데이터 번들
data: {"messageId":"msg_…","finishReason":"stop", …}

event: error                     ← 스트림 도중 실패 시 1회 (이미 200이라 상태 변경 불가)
data: {"message":"stream error"}

    done 페이로드 — 비는 필드는 JSON에서 생략된다 (contract/ChatDonePayload.java):

    필드타입의미
    messageIdstringmsg_<ts36>
    finishReason"stop" | "length"턴 종료 사유
    tables?{title?, columns?, rows: object[]}[]paired 표. columns 비면 FE가 첫 row 키로 추출
    recommendQuestion?string[]추천 후속 질문
    dataRequests?{queryKey, label, sql?, columns?}[]조달 요청 카드 — §6.4
    inputRequests?{skill, key, label, description?}[]스칼라 값 입력 카드. 회신은 inputs[skill][key]
    choiceRequests?{question, options: {label, description?}[], multiSelect}[]선택지 카드(#53). 회신은 구조화 필드 없이 클릭이 그대로 user 메시지("선택 — …")로 돌아온다
    images?{label, dataUrl?, url?, alt?}[]답에 딸린 그림 — 원격 주소·인라인 base64 둘 다
    links?{label, url, description?}[]답이 가리키는 바깥 문서

    6.4 조달 왕복 — dataRequests ↔ dataSnapshots

    BE가 DB에 붙지 못하는 환경에서, 모델이 지어내는 대신 사용자에게 조달을 요청하는 통로다. 요청 카드의 queryKey는 BE가 만든다 — {스킬}#{단계}__{인자=값&…} 꼴로, run 이름표에 필수 인자 전량이 들어가 한 절차의 모든 단계가 같은 이름표를 단다. 그래서 도착한 스냅샷만 보고 "이 절차는 몇 단계까지 왔나"가 유도된다 — chat/QueryKey.java:9-25.

    demo-fe
    브라우저 · 스냅샷 보관과 재전송 책임
    fdc-agent-be
    무상태 · 진행은 스냅샷에서 유도
    시작 사용자가 설비에 관해 질문 — 스킬의 조회 결과가 필요한 질문
    #1 · 질문 · POST /api/fdc/v1/chat

    질문 — 아직 데이터 없음

    FE {"messages":[…], "scope":{…}} 스냅샷 미동봉 — 첫 턴
    BE 내부

    스킬 spec에서 조달 카드 생성

    1. LLM 툴 루프 — 스킬 선택, 필요한 조회 식별
    2. queryKey = fdc-explain-sensor#0__snsr_id=S-0004 발급 (BE 생성)

    SQL은 spec의 것 — 모델이 자유 저작하지 않는다.

    #1 · 응답 · token* + done

    조달 요청 카드

    BE done.dataRequests: [{queryKey, label, sql, columns}] FE가 요청 카드로 렌더 — SQL 복사 버튼 제공
    FE 쪽 — 사람 손

    사용자가 사내에서 SQL 실행 → 결과 등록

    • 결과 붙여넣기 → 스냅샷이 그 queryKey로 등록 (동봉 ON)
    • 결과가 없으면 "결과 없음"으로 등록 → rows: []
    #2 · 재요청 · POST (스냅샷 동봉)

    같은 질문 + 도착한 데이터

    FE {"messages":[…], "dataSnapshots":[{queryKey, columns, rows}]} 등록된 스냅샷 전량 재전송 — 진행 판정의 유일한 근거
    BE 내부

    도착 판정 → 진행 유도

    1. 스냅샷을 임시 DB에 적재, queryKey를 다시 만들어 대조
    2. 다음 단계 바인드가 준비됐으면 다음 카드, 전부 도착이면 최종 서술
    3. 0행이면 그 절차는 정상 종료 — "그 조건으로는 데이터가 없다"
    #2 · 응답 · token* + done

    다음 카드 또는 완주 답변

    남은 단계가 있으면 같은 왕복이 반복된다 — 카드가 더 안 나오면 완주.

    끝 모든 단계 도착 → 데이터를 근거로 한 최종 서술

    queryKey는 BE가 만든다

    {스킬}#{단계}__{인자}. 키가 안정적이어서 재요청 억제가 정확 일치로 동작하고, 키 자체가 진행 상태를 들고 있다.

    서버는 무상태

    진행을 저장하지 않는다. 그래서 FE는 등록된 스냅샷을 매 요청 전량 재전송해야 한다 — 빠뜨린 스냅샷은 "안 도착"으로 보인다.

    0행도 도착이다

    없음을 확인한 것과 아직 안 온 것은 다르다. 0행은 답의 근거가 되고 재요청을 멈춘다.

    스냅샷 내용은 데이터지 지시가 아니다

    사용자가 붙여넣은 임의 텍스트가 들어오는 자리 — 그 안의 문장을 프롬프트 지시로 해석하지 않는다.

    6.5 chat 의 에러 경로

    시점형태예
    검증 실패 (스트림 전) 400 + JSON {"error":"messages_too_many","limit":100,"actual":120}
    에이전트 실행 실패 (스트림 전) 4xx/500 + JSON {"error":"chat_failed","message":"…"} — prod에서는 메시지 마스킹
    스트림 도중 실패 SSE event: error {"message":"stream error"} — 이미 200이라 상태 변경 불가, 상세는 서버 로그에만

    7. 에러 형식

    모든 4xx/5xx는 application/json으로 다음 꼴이다 — config/ApiExceptionHandler.java:

    {
  "error": "코드",        // machine-readable
  "message": "…",         // 선택 — prod의 500은 "internal error"로 마스킹
  "limit": 100,           // 한도 위반일 때만
  "actual": 120
}
    코드HTTP언제
    invalid_json400본문 파싱 실패
    messages_required400chat — messages 누락/빈 배열
    messages_too_many400chat — 100개 초과
    message_content_too_long400chat — 10,000자 초과
    not_found404없는 경로
    chat_failed4xx/500chat — 에이전트 실행 실패(스트림 시작 전)
    internal500그 외 서버 오류

    prod(fdc.env=production)에서 500의 message는 "internal error"로 고정된다 — 상세는 같은 x-request-id의 서버 로그에서.
